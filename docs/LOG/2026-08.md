- **What actually changed relative to the retired work is three characters
  and their consequences.** #226 was parked after two arbiter rejections that
  were the same finding at the same site both times — the dropped `_` in
  `prefix, _ := br.Peek(bomLen)` inside `decodeBOM`. `decodeBOM` now captures
  that error, and when it is non-nil and not `io.EOF` wraps the body in a new
  unexported `latchedErrReader`: it serves whatever bytes `Peek` had already
  buffered, then reports the latched error once the buffer drains, **without
  ever touching the underlying source again**. The mechanism note is in the
  code and is the load-bearing part —
  `bufio.Reader.Peek` takes its error from `readErr`, which does
  `err := b.err; b.err = nil`, so the peek is the *last* place that error is
  visible.
- **The regression this closes is a diagnostics regression against `main`, not
  a false-accept.** A source failing on its very first read — a broken disk, a
  reset connection — made `Token()` return bare `io.EOF`, which `reader.go`
  documents as a well-formed empty document, so the user got
  `[xml-wf] document has no root element` where the real cause was
  `[xml-wf] boom: original cause`. Two new regression tests pin it:
  `TestSourceFailureSurfacesItsCause` (xmltree, two arms — fails before a mark
  can be read, and fails after a mark is ruled out) and
  `TestReadDocumentSourceFailureSurfacesItsCause` (parser, end to end,
  asserting `errors.Is(err, cause)`, the `RuleXMLWellFormed` charge, the
  document URI on the `Loc`, and explicitly that the message does **not**
  contain "no root element").
- **Spec**: XML 1.0 §4.3.3 (`docs/specs/md/xml.md`) + non-normative Appendix
  F.1 for the mark byte sequences. The grounding was #226's, reused unchanged
  and not re-derived: a mark alone is sufficient evidence of an entity's
  encoding, a declaration that IS present must agree, and a mark/declaration
  conflict is a fatal well-formedness error → `xsderr.RuleXMLWellFormed`.

- Surprises — **mason found a real bug in the carried-forward text that two
  rounds of review on #226 had not caught, and it was a genuine bug, not a
  garble introduced by the port.** `checkDeclaration`'s message read
  `"encoding declaration %q disagrees with the %s byte-order mark"` with
  `%s` = `bomEncoding`, whose `String()` returns *"a UTF-16 big-endian
  byte-order mark"* — so the literal carried-forward text would have rendered
  as "disagrees with the **a UTF-16 big-endian byte-order mark** byte-order
  mark". The message now reads "disagrees with the entity's actual encoding:
  %s", and `String()`'s doc comment says why it names the evidence rather than
  the mark. The general shape: **carrying code forward from a retired branch
  means re-reading it, not re-applying it** — a branch that was rejected twice
  on one site can still be wrong somewhere nobody looked, because review
  attention pooled where the rejection was.
